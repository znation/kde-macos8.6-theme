## Planned

### Reference-pixel sampler: isolate scalar argument parsers (planned 2026-11-03 by the plan role)

**Goal.** Keep the sampler's growing CLI definition readable by separating scalar conversion from option construction and compatibility checks. `tools/sample_arguments.py` currently combines six scalar parsers with `build_parser`, `option_error` and `region_error`; the finished compatibility-validation plan moved checks out of image loading, rather than separating these responsibilities.

**Approach and files.** Move `rgb_argument`, `color_tolerance`, `match_alpha`, `match_pixels`, `match_pixel_offset` and `color_fraction` without semantic changes into new `tools/sample_argument_types.py`. Move their `argparse`, `math`, `re` and `plain_number` imports with them. Import the six names into `tools/sample_arguments.py` in its package and direct-script branches, retaining existing import access there; leave `positive_int`, parser construction and the two namespace validators in place. Add focused `tests/test_sample_argument_types.py` using unittest. No CLI option, report format or theme value changes are proposed. These three files bound the implementation; existing tooling guarantees in `docs/invariants.md` remain applicable.

**Acceptance criteria.** Direct scalar calls accept RGB `#aBcD09` as `(171, 205, 9)`, byte endpoints 0 and 255, match limits 1 and 1000, offset 0 and fraction endpoints 0 and 1. They reject malformed RGB, byte values -1/256, match limits 0/1001, negative offsets, fractions outside [0,1] and non-finite fractions with `ArgumentTypeError`; numeric parsers continue rejecting non-ASCII digits. Imports through `tools.sample_arguments` still expose the six parsers. Package and direct-script CLI invocations accept a valid search and histogram request on a tiny PNG with the same parsed JSON results, and reject invalid scalar inputs with status 2, empty stdout and the existing diagnostic content. Existing option-validation tests continue to show compatibility errors before image reads. `make check` passes.


### Fidelity diagnostics: page through ranked worst pixels (planned 2026-11-03 by the plan role)

**Goal.** Inspect later severe mismatches without changing the compared crop or tolerance. `tools/fidelity_pixels.py::worst_pixels` currently retains the first N ranked mismatches; source searches and the finished worst-pixel plans cover that first page and source coordinates, but not a ranked offset. This work is independent of the waiting sampler parser extraction.

**Approach and files.** Add `--worst-pixel-offset K` in `tools/fidelity_cli_parser.py::build_parser`, defaulting to None, with a new ASCII-decimal nonnegative validator in `tools/fidelity_arguments.py`. In `tools/fidelity.py::main`, reject explicit use without `--worst-pixels` before source reads. Extend `tools/fidelity_pixels.py::worst_pixels` with keyword-only `offset=0`: retain the first `offset + limit` ranked candidates using the existing generator/heap selection, then construct records for the slice starting at offset. Clamp selection size to the compared pixel area before calling `heapq.nsmallest`. Ranking and tolerance apply before pagination; source-position translation and existing report formats need no changes. Document that selection storage grows with the requested offset plus page size, bounded by image area; this is report pagination, not reduced decoding or comparison work. Extend `tests/test_fidelity_pixels.py` and `tests/test_fidelity_cli_parser.py`, document the flag beside `--worst-pixels` in README.md, and update the worst-pixel guarantee in `docs/invariants.md`. Keep the implementation to these eight files and a few hundred changed lines; no report metadata or additional pagination feature is needed.

**Acceptance criteria.** Given a 3x2 opaque candidate with red values `[9, 5, 9, 0, 7, 9]` over a black reference, tolerance 5, limit 2 and offset 1, records are `(2,0,9)` then `(2,1,9)` in `(x,y,max_delta)` form; offset 3 returns only `(1,1,7)`, and offsets 4 and 100 return an empty list. Offset 0 produces the existing first-page records. Cover an alpha-only mismatch and RGB under zero alpha, plus different nonzero candidate/reference crop origins whose returned source positions identify the selected page's pixels. JSON and text expose the selected records, including an empty page; full-region metrics, verdict and exit status agree with the same comparison without an offset, including an aggregate-budget PASS. Package and direct-script invocations accept the option. Negative, fractional, empty and non-ASCII offsets, and an explicit offset without `--worst-pixels` (including zero), produce status 2 and empty stdout before image reads. Omitting the option preserves existing first-page output and the default no-report behavior. `make check` passes.

### Reference-pixel sampler: isolate rare histogram colors by maximum count (planned 2026-11-03 by the plan role)

**Goal.** Find sparse edge and accent colors without enumerating dominant background RGB values. Searches of sampler code, tests and plan headings found minimum-count and named-color exclusion support, but no maximum-count option.

**Approach and files.** Add optional `--max-color-count N` (positive ASCII integer, absent by default) in `tools/sample_arguments.py::build_parser`; in `option_error`, reject use without `--histogram` immediately after the existing minimum-count compatibility check. In `tools/sample_report_histogram.py::_histogram_result`, retain counts at most N before top-color selection, intersecting with exclusions and minimum-count/fraction predicates. Include this option in the filtered-report conditions in `_histogram_result` and `report_histogram`, so explicit use emits original `total_colors` and `omitted_pixels` even when nothing is removed. Contradictory minimum/maximum cutoffs produce a successful empty palette rather than a new validation error. Add `tests/test_sample_histogram_max_count.py` using `CliTestCase` and synthetic PNG fixtures; extend `tests/test_sample_option_validation.py::TestSampleOptionValidation` for compatibility ordering. Document the option in README.md's sampling section and add its guarantee/test to docs/invariants.md. This is one bounded CLI/report change, independent of the waiting scalar-parser extraction; use the existing `positive_int` facility without moving converters.

**Acceptance criteria.** In an eight-pixel crop with RGB counts 3, 2, 2 and 1, maximum 2 emits counts 2, 2 and 1 in descending count/ascending tuple order, with `total_colors=4` and `omitted_pixels=3`; adding `--top-colors 1` emits the earlier tuple among the count-2 colors and reports six omitted pixels. Minimum 2 plus maximum 2 emits both count-2 colors; minimum 3 plus maximum 2 emits an empty palette and eight omitted pixels. Maximum 8 retains the complete palette with explicit totals; omitting the new option retains the existing report schema. Tests exercise intersection with exclusions and minimum fraction, and verify emitted-color fractions still divide by eight and spatial coordinates remain absolute within an offset crop. An RGBA fixture with one RGB split across alpha levels proves the cutoff applies to separate RGBA counts under `--alpha`, while ordinary RGB mode merges them. Text and JSON report the same retained colors and totals, and direct-script and package entry points agree. Zero, negative, fractional, non-ASCII and missing values, or use in pixel/run/search mode, exit 2 with empty stdout before PNG reads; incompatible mode use names `--max-color-count requires --histogram`. Existing compatibility precedence remains intact. Run `make check` after final edits.
