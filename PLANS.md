The tree carries the removal driver in `tools/kvantum_selection.py` (`TOOL = "remove_kvantum"`, direct and `python3 -m` usage) with all the listed behaviors — `xdg_homes.config_home` resolution with exit 2 naming `HOME`/`XDG_CONFIG_HOME`, absent-file success, byte-identical passthrough for foreign/empty/absent values, symlink refusal, atomic write, the fallback note with provenance in docs/invariants.md — plus `Makefile::remove-kvantum` with `.PHONY` and help rows, the README installing/uninstall/removal-table prose, the `## kvantum` invariant row naming `tests/test_remove_kvantum.py` and `tests/test_kvantum_selection_make.py`, and an uninstall diagnostic. Re-implementing would duplicate a module; the plan role should dedupe or redirect this entry.

**Refused 2026-11-04 by the plan role: the landed sibling plan already ships this whole feature — `make remove-kvantum`, the standalone `tools/kvantum_selection.py` CLI (Usage lines for direct and `python3 -m` runs, absent-file and foreign-value notes, `exclusive_flock` over the config home, symlink refusal), the README Removing-the-theme table row and Installing prose all exist — and this entry's different chassis (`tools/remove_kvantum.py`, explicitly no lock) would duplicate the tool and regress the landed lock guarantee.

**Goal and grounding.** `make apply` points the Kvantum engine at this theme — `tools/theme_apply_optional.py::select_kvantum_theme` runs `kvantummanager --set org.macos8.desktop`, which stores the choice as `[General] theme=org.macos8.desktop` in `$HOME/.config/Kvantum/kvantum.kvconfig` (layout confirmed on this host, and the render session already reads that literal file — see the archived scratch-session outcome referencing `Kvantum/kvantum.kvconfig`). `make uninstall` later deletes the installed widget style, and no make target or README row clears that selection, so widgets silently keep resolving a deleted theme. The removal story covers GTK (`tools/gtk_selection.py::remove`), Firefox (`tools/firefox_profile_actions.py::remove_profile`) and cursor (`tools/cursor_workflow.py::remove`) but not the engine selection; this entry mirrors those patterns. Clearing a KDE/Qt color scheme or global theme stays out: that is the user's choice made in System Settings, already documented.

**Approach and files.** Add `tools/remove_kvantum.py`, a focused CLI following `apply_gtk.py --remove`'s shape: resolve the config home with `tools/xdg_homes.py::config_home` (refusing, exit 2, when `HOME` is unset or not absolute, naming it), read `config_home/Kvantum/kvantum.kvconfig` (a checked-in symlink outside the repository is refused as elsewhere; the file lives outside the repo so only absent-file and unreadable cases arise), and when the `[General]` theme value is exactly `org.macos8.desktop`, atomically rewrite the file without that key line, keeping every other byte identical (reuse `tools/gtk_settings.py::remove_theme_name`'s line-surgery style and `tools/atomic_write.py`); when the value is foreign, empty or absent, leave the file byte-identical; when the file is absent, succeed with a note. Every outcome other than a clear rewrite prints an `apply-gtk`-style stderr note naming the path: absent file ("nothing to clear"), foreign or absent value ("left untouched"), and after clearing, that widgets draw the engine's built-in default theme on their next start following this removal (the implementer grounds that fallback claim against the upstream Kvantum 1.1.4 sources the project already reads for Kvantum adaptations, and records it like those adaptations — it is prose provenance, not a rendered-pixel assertion). Single file, single atomic replace, so no lock is added. Add Makefile target `remove-kvantum` (`require_python_ready` only; no DESTDIR guard or data-home lock — nothing under the data home is touched) with a `.PHONY` and help entry, so the help-pinning check stays exhaustive. Add a `## tooling` row in docs/invariants.md and its `tests/support/invariants.py` register entry, plus a `tests/test_remove_kvantum.py` module using the existing isolated-homes make-run support. README.md gains a `remove-kvantum` row in the Removing-the-theme table (clears only the engine selection; `make uninstall` still deletes the widget style; restart running Qt applications) and prerequisites prose stays as is. Existing `tests/test_apply_*` and Kvantum config tests stay byte-unchanged.

**Acceptance criteria.** With an isolated config home, `make remove-kvantum` on a `Kvantum/kvantum.kvconfig` holding `[General] theme=org.macos8.desktop` beside unrelated keys exits 0, leaves the file with every other byte identical and only the theme key removed, and prints the clearing note naming the path. With `theme=KvArc` (a foreign name), `theme=` (empty), a `[General]` without `theme`, or no file at all, the run exits 0, the disk file when present is byte-identical, and the note explains nothing of ours was cleared (absence notes the literal missing path). An unset or relative `HOME` with no absolute `XDG_CONFIG_HOME` exits 2 with a diagnostic naming `HOME`. Re-running after removal is idempotent (second run notes nothing to clear, bytes unchanged), and `make apply` afterwards re-selects the theme, so a clear-then-apply round trip works. `remove-kvantum` appears in `.PHONY` and `make help`; the README row and the new invariant row pass their register checks; `make check` is green after the final edit.

### Diagnose the pointer selection left behind by `make uninstall` (planned 2026-11-04 by the plan role)

**Goal and grounding.** Every selection `make apply` publishes gets an uninstall diagnostic in `Makefile`'s `_uninstall` block: `kdeglobals`' color scheme (reset `plasma-apply-colorscheme BreezeLight`), the GTK `settings.ini`/`gtk.css` selections (reset `make remove-gtk`), and the Kvantum kvconfig selection (reset `make remove-kvantum`). The pointer selection has none: `make apply-cursor` runs `plasma-apply-cursortheme` (`tools/cursor_link.py::CURSOR_THEME = "org.macos8.desktop"`), which writes `[Mouse] cursorTheme` in `$XDG_CONFIG_HOME/kcminputrc`, `make uninstall` deletes the installed icon theme under `Makefile`'s `ICON_THEME_ID`, and afterwards Xcursor silently keeps the default pointer — the same silent-fallback gap the other three diagnostics close. `tools/cursor_config.py::cursor_theme_setting` documents exactly how kcminputrc is read (`utf-8-sig`, `[Mouse]` section, `cursorTheme` key, comments never keys), and `tools/cursor_workflow.py::remove`'s note names the reset (`run plasma-apply-cursortheme breeze_cursors to reset`) — but it only fires on an explicit `make remove-cursor`, never after `make uninstall`. Grep of `Makefile`, README.md, PLANS.md, PLANS-DONE.md and BUGS.md found no uninstall diagnostic for kcminputrc, only the removal-time note.

**Approach and files.** Makefile, one new test module, docs/invariants.md and README.md. In `_uninstall`, after the existing kvconfig guard block and reusing the already-resolved `$$config_home`, add a fourth diagnostic: when `$config_home/kcminputrc` is a regular file, an awk that mirrors the three existing awk scanners — strip the first line's UTF-8 BOM, trim each line before parsing, a trimmed `[`…`]` line switches the section, `#`/`;` lines are comments and never keys, key/value split at the first `=` with both sides trimmed, and the last duplicate's value wins — recognizes a `[Mouse]` section `cursorTheme` whose value trims to `$(ICON_THEME_ID)` and prints on stderr exactly: `uninstall: the pointer selection still names $(ICON_THEME_ID) after removal in <kcminputrc>; Xcursor applications cannot load the removed cursor theme and keep the default pointer. Reset it with: plasma-apply-cursortheme breeze_cursors` — diagnostic only, never editing the file, and unlike the two make-target resets this one names an external command because `tools/cursor_workflow.py::remove` deliberately leaves kcminputrc untouched and `make remove-cursor` owns only the `$HOME/.icons` link (it also clears nothing of the selection, so the color-scheme-style external reset is the proven pattern). `breeze_cursors` is KDE's default pointer theme, a platform-required value inherited from the existing removal note; no reference screenshot shows a pointer, so no pixel is sampled. Precede the new awk with a comment paragraph in the style of the existing `_uninstall` comment block recording the scanner semantics and the never-edit rule. The three existing awk diagnostics and their wordings, `tools/cursor_config.py`, `tools/cursor_workflow.py`, `tools/cursor_link.py` and the removal path stay byte-identical.

**Tests.** New `tests/test_cursor_uninstall_diagnostic.py`, driving `make uninstall` through `tests/support/theme_install.py::run_make` on a temp `DESTDIR` with a throwaway config home, in the pattern of `tests/test_colorscheme_install.py` and the kvconfig-diagnostic tests in `tests/test_remove_kvantum.py`.

**Acceptance criteria.**

- After `make uninstall` on a host whose freshly written kcminputrc holds `[Mouse] cursorTheme=org.macos8.desktop` between unrelated lines, the run exits 0, prints on stderr the exact reset line above with the real absolute path substituted, and the file reads back byte-identical; comments and CRLF line endings around the key do not change this, and a BOM-prefixed file is still recognized.
- A foreign value (`cursorTheme=breeze_cursors`), an empty value, `cursorTheme` under any other section, a key of a different name in `[Mouse]`, and an absent or unreadable kcminputrc each print nothing and leave `make uninstall` succeeding; with both `XDG_CONFIG_HOME` unset and `HOME` unset the guard stays empty and nothing is checked; with `XDG_CONFIG_HOME` relative and `HOME` absolute nothing is checked, matching the existing blocks' behavior.
- A duplicate key where our id appears on an earlier line and `breeze_cursors` on the later one is silent; the reverse order fires; a value that only trims to our id (surrounding spaces) still fires.
- The color-scheme, GTK and kvconfig diagnostic tests still pass with their exact existing wordings; `make -n uninstall` still parses. README.md documents the pointer diagnostic and its reset beside the existing Kvantum/KGTK uninstall-warning prose, and docs/invariants.md's cursor row names the new test module in its tests column. `make check` passes after the final edit.

### Warn when the Kvantum selection can only resolve from the default data home (planned 2026-11-04 by the plan role; independent of the waiting uninstall pointer-diagnostic entry — that entry edits the Makefile `_uninstall` awk block, a new uninstall test module and the README uninstall prose, while this entry edits `tools/theme_apply_optional.py::select_kvantum_theme`, `tools/xdg_homes.py`, the apply-test module and the README Installing/apply-plasma prose, so the two touch disjoint files and regions and can merge in either order)

**Goal and grounding.** `make install` copies the Kvantum widget style into `$XDG_DATA_HOME/themes/org.macos8.desktop/Kvantum/`, and `tools/theme_apply_optional.py::select_kvantum_theme` selects it with `kvantummanager --set` — but Kvantum resolves its theme directory only through the literal `$HOME/.local/share/themes/<name>/Kvantum/` path (README's Installing section states this: "Kvantum searches `$HOME/.local/share/themes/<name>/Kvantum/` with that literal path, so it finds the theme only when `${XDG_DATA_HOME}` is the default"), and the make render scratch-session plumbing works around the same fact with a literal themes link. With a non-default absolute `XDG_DATA_HOME`, both the selection write and the apply succeed yet the engine silently draws its built-in default theme: a documented limitation with no warning at the moment the user makes the choice. The right remedy is a note at selection time, mirroring the missing-`kvantummanager` note the same function prints; grep of PLANS.md, PLANS-DONE.md, BUGS.md and BUGS-FIXED.md found no entry covering an apply-time data-home warning (the archived apply-plasma plan only repeats the limitation in prose), and the rollback/lock plans own other behaviors.

**Approach and files.** Two source files plus tests and prose. In `tools/xdg_homes.py`, add a pure `default_data_home(env) -> Path | None` beside `data_home`: the `$HOME/.local/share` child resolved the same way `data_home` falls back (None when `HOME` is unset or not absolute); no existing function or behavior changes. In `tools/theme_apply_optional.py::select_kvantum_theme`, after the `kvantummanager` presence check succeeds and before the selection runs, resolve `data_home(env)` and `default_data_home(env)` and, when both are not None and the resolved home differs from the default, print via the existing `_note` exactly: `the Kvantum engine reads its theme directory only under the default data home <default>, not the resolved <resolved>; widgets draw Kvantum's built-in default theme until themes/org.macos8.desktop/Kvantum exists there` with the two real absolute paths substituted — the selection itself runs unchanged either way, and the note never changes the exit status, keeping every note in this module best-effort. A None resolved home (no usable `HOME` in the apply's env) or a None default skips the check silently. `make apply-plasma`, which runs the same `tools/apply_theme.py`, inherits the note unchanged. README.md updates the two "existing default-data-home limitation" sentences (the apply-plasma paragraphs at the Installing and aggregate-apply spots) to name the apply-time note, and the Installing Kvantum paragraph gains a sentence stating that running `make apply` with a non-default `XDG_DATA_HOME` prints this note; docs/invariants.md's `## kvantum` table gains a row naming the new test.

**Tests.** Extend `tests/test_apply_theme.py` beside the existing `test_missing_kvantummanager_prints_a_note_and_exits_0` stub class with a new test class driving `select_kvantum_theme` through the same stub-`kvantummanager` machinery (same stubbing pattern `StubTools` uses): one test per env shape below, asserting exit status 0, the exact note line and, for the silent cases, that stderr carries no data-home note. Also add a small `tests/test_xdg_homes.py` class for `default_data_home`: absolute/absolute-set `HOME`, unset `HOME`, and relative `HOME`.

**Acceptance criteria.**

- With a stubbed `kvantummanager` found on the stubbed `PATH` and an env whose `XDG_DATA_HOME` is an absolute non-default path (e.g. a scratch directory), the selection exits 0, the stub records the unchanged `--set org.macos8.desktop` argv, and stderr ends with exactly the note line above with both rendered paths — no other line of the apply's output changes.
- With no `XDG_DATA_HOME` at all, an empty `XDG_DATA_HOME`, or a relative one, and with the data home equal to the default, no such note appears and the selection behaves identically to today (exit 0, unchanged argv). When the compare cannot resolve both sides — an `XDG_DATA_HOME` that is empty or relative with a `HOME` unset or relative, or an absolute `XDG_DATA_HOME` with a `HOME` unset or relative (the resolved home comes from `XDG_DATA_HOME` alone but no default exists to name) — the check skips silently too.
- With `kvantummanager` absent, the existing missing-tool note and status are byte-identical to today and no data-home note is printed; with the manager present on a non-default data home and the stub broken (non-zero exit), both the data-home note and the selection-failure note appear and the status stays 0.
- `tools/xdg_homes.py::default_data_home` returns `<absolute HOME>/.local/share` given an absolute `HOME` and None for an unset or relative `HOME`, regardless of what `XDG_DATA_HOME` holds (unlike `data_home`, which answers an absolute `XDG_DATA_HOME` with no `HOME`); the existing `xdg_homes` behaviors (data home resolution, empty/relative `XDG_DATA_HOME` fallback) read back unchanged. README prose and the invariant row pass their register checks; existing apply tests keep passing with unchanged stubs; `make check` is green after the final edit.

### Reference-pixel sampler: cap the vertical color-match interval report (planned 2026-11-04 by the plan role) — done 2026-11-04 by the feature role

**Goal.** Bound noisy `--find-color --match-column-runs` output while retaining full-region measurements. Source and archive-heading searches found vertical length filters and counts, and horizontal output caps, but no vertical color-match interval cap. This complements the preceding horizontal-cap entry and can merge independently: the vertical filter and report blocks already exist.

**Approach and files.** In `tools/sample_arguments.py::build_parser`, add optional `--max-match-column-runs N`, default None, using `positive_int`; `option_error` requires `--match-column-runs`. In `tools/sample_report_search.py::_search_match`, slice the completed column-major list after both inclusive vertical length filters and add `match.omitted_column_runs` (eligible count minus emitted count) when the cap is explicit, including zero. In `report_search`, print `omitted matching column runs: N` immediately after the vertical list. Keep `tools/sample_match_runs.py::_MatchRuns` unchanged: its count and longest summary precede report filtering, and `finish` sorts by `(x,y)`. This bounds output, not segmentation memory. Add `tests/test_sample_match_column_runs_limit.py` using `CliTestCase` and the generated PNG pattern in `TestSampleMatchColumnRunsMaxLength`; document the flag beside vertical filters in README.md and extend the vertical-filter tooling row in docs/invariants.md. These five changed files constitute one run; pagination and collector optimization are outside this plan.

**Acceptance criteria.**

- For a 2x9 crop at absolute origin (2,1), column zero matches relative rows {0,2,3,5,6,7} and column one matches {8}. Cap 2 emits exactly `(2,1,1)` and `(2,3,2)` as `{x,y,length}` records with 2 omitted. Cap 3 adds `(2,6,3)` with 1 omitted, detecting a cap restarted per column. Maximum length 2 plus cap 2 emits the leading pair with 1 omitted; minimum length 2 plus cap 1 emits `(2,3,2)` with 1 omitted. Contradictory length cutoffs yield an empty list with zero omitted. Cap 4 or larger includes the bottom-flushed `(3,9,1)` and reports zero omitted; no matches produce an empty list with zero omitted.
- With summaries requested, count remains 7, column-run count remains 4 and longest column run remains `(2,6,3)` despite capping. Bounds, fraction, centroid, horizontal intervals, row/column diagnostics and coordinate paging match uncapped results. Include adjacent unequal RGB values accepted by tolerance and an exact-alpha rejection that splits an interval, checking literal capped records; stored RGB beneath alpha zero remains searchable. JSON and text expose the same prefix and omitted count. Without the option, neither the new member nor text line appears.
- Zero, negative, fractional, malformed, non-ASCII and missing caps exit 2 with empty stdout. A valid cap with `--find-color` but without `--match-column-runs` fails before reading a missing image and names the required flag. Help describes the dependency; direct-script and package output agree. README distinguishes interval count from pixel length and states filtering precedes capping; the invariant row names the new tests. `make check` passes after the final edit.
