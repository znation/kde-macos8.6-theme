## Planned

### Add `make remove-kvantum` clearing the Kvantum selection (planned 2026-11-04 by the plan role)

**Goal.** `make apply` selects the Kvantum widget theme with `kvantummanager --set org.macos8.desktop` (`tools/theme_apply_optional.py::select_kvantum_theme`), which writes the user's `$XDG_CONFIG_HOME/Kvantum/kvantum.kvconfig`: `[General] theme=org.macos8.desktop` (verified on this host 2026-11-04 — the file is 35 bytes, exactly that selection). Every other selected surface has a removal and an uninstall diagnostic: `make remove-gtk`, `remove-cursor` and `remove-firefox`, and `make uninstall`'s awk block prints a dangling-selection diagnostic naming each reset command (color scheme, then GTK). The Kvantum selection has neither: after `make uninstall` a Qt application silently draws Kvantum's compiled-in default, and the only route out is editing the selection file by hand. `make install` correctly leaves it alone (a selection the user wrote through System Settings must survive an uninstall), so the missing piece is a removal target plus the matching uninstall diagnostic — one change, because the diagnostic names the reset command, so neither is shippable without the other.

**Approach and files.**

1. New `tools/kvantum_selection.py`: a pure transform plus a small driver. `remove_theme(text) -> tuple[str, bool]` mirrors `tools/gtk_settings.py::remove_theme_name` for the `[General]` section and the `theme` key: strip a leading UTF-8 BOM for matching and write it back, reuse the generic line/section scanners (`_split_bom`, `_split_lines`, `_join_lines`, `_section_name`, `_key_name`, `_ENDINGS`) imported from `tools.gtk_settings` unchanged so mixed endings, comments (`#`/`;`) and a `[:no close]` header behave exactly as the GTK tests pin them; delete only lines whose key is `theme` in `[General]` whose value trims to exactly `org.macos8.desktop` (constant `KVANTUM_ID`, the same id `Makefile`'s `KVANTUM_ID` and `tools/theme_apply_optional.py::KVANTUM_THEME` name), keep every other line byte-identical with its own ending, and return the text unchanged when nothing matched. The docstring keeps the existing scanner semantics documented; `tools/gtk_settings.py`'s behavior itself must not change — its tests pin it.
2. The same module carries the driver (`TOOL = "remove_kvantum"`, exit statuses in the module docstring, `Usage::` line for direct and `python3 -m` runs): resolve the config home with `tools/xdg_homes.py::config_home`, refusing with exit 2 and the same unset/empty/relative wording style `tools/apply_gtk.py`'s home-resolution refusals use (the message names `XDG_CONFIG_HOME` and `HOME`); serialize with `tools/file_lock.py::exclusive_flock` over the config home's parent directory, `LOCK_TIMEOUT = 60.0` mirroring `apply_gtk.py::_config_lock`, timing out with exit 2; refuse (exit 2, naming the path, before opening the target) a `Kvantum` directory or `kvantum.kvconfig` path in the config home that is a symbolic link, in the precedent of `tools/symlink_refusal.py` and `apply_gtk`'s symlink refusals; publish with `tools/atomic_write.py` after a successful read, so a mid-run failure leaves the previous file intact; and create nothing — an absent config home, absent `Kvantum/` directory or absent `theme` key exits 0 without writing anything. The removal never touches the data home or the installed theme files, and never adds or removes any other kvconfig key (`kvantummanager` owns the rest of that file).
3. `Makefile`: a public `.PHONY` target `remove-kvantum` shaped like `remove-gtk` (`require_python_ready`, then `$(PYTHON) tools/kvantum_selection.py`; no install prerequisite, no `DESTDIR` word), its `help` echo line, and a third dangling-selection diagnostic in the `_uninstall` block inside the existing `if [ -n "$$config_home" ]` chassis: an awk over `$config_home/Kvantum/kvantum.kvconfig` that recognizes a `[General]` section `theme` whose value trims to the id (same header/trim/comment semantics as the two existing awk diagnostics, and taking the last duplicate's value like the color-scheme one), printing to stderr `uninstall: the Kvantum selection still names $(KVANTUM_ID) after removal in <path>; Kvantum applications cannot load the removed theme and keep their default style. Clear it with: make remove-kvantum` — diagnostic only, never editing the file. The two existing color-scheme and GTK diagnostics must stay byte-identical.
4. `README.md`: beside the Installing prose that documents `make remove-gtk` and the Kvantum selection (`kvantummanager --set`, the `theme/kvantum/org.macos8.desktop/` art, the `$HOME/.local/share/themes/<name>/Kvantum/` search path), document `make remove-kvantum`: it clears only our `[General] theme=org.macos8.desktop` selection in `$XDG_CONFIG_HOME/Kvantum/kvantum.kvconfig`, leaving a foreign theme name and the rest of the file byte-identical; restart running Qt applications afterwards. State that `make uninstall` leaves that selection in place for System Settings users and names this reset when it still points at the removed theme.
5. `docs/invariants.md`: one row in the existing `## kvantum` table for the selection-removal guarantee, naming the new tests as its test and recording the provenance exception (the selection-file format, the `[General]`/`theme` key names and the id are Kvantum- and KDE-required platform values the reference screenshot set does not show; observed in the real `kvantummanager`-written file on this host 2026-11-04).

**Tests.** `tests/test_remove_kvantum.py` (transform + driver, run in-process under a throwaway config home in the style of `tests/support/apply_gtk_case.py` and `tests/support/cli_fixtures.py::run_main`), and `tests/test_kvantum_selection_make.py` (Makefile target and uninstall diagnostic through `tests/support/theme_install.py::run_make`/`uninstall` on a temp `DESTDIR`, in the pattern of `tests/test_colorscheme_install.py`). Pin: our key removed while a foreign `[General]` key, other sections' keys, comments and CRLF line endings read back byte-identical; a foreign `theme` value and a matching name under any other section untouched with exit 0 and an unchanged file; every duplicate matching line removed (the last of them included); a BOM-prefixed and an indented-header file handled; exit 0 with no `Kvantum/` directory or file created when none exists; a symlinked selection file refused without following it; an unresolvable config home exits 2 naming `XDG_CONFIG_HOME`/`HOME`; a lock held by another run times out with exit 2 naming `remove-kvantum`; `make -n remove-kvantum` prints the script, `make help` lists it; the uninstall diagnostic fires only when the selection still names the id (last-duplicate winner), prints the exact reset command above, does not fire for a foreign theme or an overridden earlier match, and leaves the kvconfig unedited.

**Acceptance criteria.**

- Given a `kvantum.kvconfig` containing `[General] theme=org.macos8.desktop` among foreign lines, `make remove-kvantum` exits 0 and the file reads back with our line gone and every other byte identical, including mixed line endings and a preserved BOM; a second run exits 0 and changes nothing; with no kvconfig present, it exits 0 and creates neither the `Kvantum/` directory nor the file; with `theme=KvBreezeDark` (or our id under a non-`[General]` section), it exits 0 and the file is byte-identical. A `Kvantum/kvantum.kvconfig` that is a symlink exits 2 with a message naming the path, and nothing is read from or written to the link target.
- When the removal cannot take the config-home lock within its bounded wait, it exits 2 with a message naming `remove-kvantum`; when `XDG_CONFIG_HOME` is relative and `HOME` is unset, it exits 2 naming both rather than guessing a path.
- After `make uninstall` on a host whose kvconfig still names `org.macos8.desktop`, the run succeeds and prints on stderr the exact `Clear it with: make remove-kvantum` diagnostic above, and the kvconfig is unchanged; a foreign selection (or an earlier `org.macos8.desktop` key overridden by a later foreign one) prints nothing; the two existing kdeglobals and GTK diagnostics still fire as their tests pin.
- `make help` lists `remove-kvantum`; README.md documents the removal and the uninstall reset next to the Kvantum selection prose; docs/invariants.md's `## kvantum` table gains the row naming the new tests; `tools/gtk_settings.py`, `tools/apply_gtk.py`, `tools/theme_apply_optional.py`, `tools/render_setup.py` and the two existing uninstall diagnostics are byte-unchanged; `make check` passes after the final edit.

### Offer a standalone Kvantum selection removal command (planned 2026-11-04 by the plan role; independent of the waiting README apply-guidance entry — that entry edits only the Installing aggregate-apply prose, while this entry adds a tool, a Makefile target and a Removing-the-theme table row, so the two touch disjoint README regions and can merge in either order; the archived optional-integrations extraction covers apply-side choice, not removal, and searches of this queue and the archive headings found no Kvantum-selection removal entry)

**Goal and grounding.** `make apply` points the Kvantum engine at this theme — `tools/theme_apply_optional.py::select_kvantum_theme` runs `kvantummanager --set org.macos8.desktop`, which stores the choice as `[General] theme=org.macos8.desktop` in `$HOME/.config/Kvantum/kvantum.kvconfig` (layout confirmed on this host, and the render session already reads that literal file — see the archived scratch-session outcome referencing `Kvantum/kvantum.kvconfig`). `make uninstall` later deletes the installed widget style, and no make target or README row clears that selection, so widgets silently keep resolving a deleted theme. The removal story covers GTK (`tools/gtk_selection.py::remove`), Firefox (`tools/firefox_profile_actions.py::remove_profile`) and cursor (`tools/cursor_workflow.py::remove`) but not the engine selection; this entry mirrors those patterns. Clearing a KDE/Qt color scheme or global theme stays out: that is the user's choice made in System Settings, already documented.

**Approach and files.** Add `tools/remove_kvantum.py`, a focused CLI following `apply_gtk.py --remove`'s shape: resolve the config home with `tools/xdg_homes.py::config_home` (refusing, exit 2, when `HOME` is unset or not absolute, naming it), read `config_home/Kvantum/kvantum.kvconfig` (a checked-in symlink outside the repository is refused as elsewhere; the file lives outside the repo so only absent-file and unreadable cases arise), and when the `[General]` theme value is exactly `org.macos8.desktop`, atomically rewrite the file without that key line, keeping every other byte identical (reuse `tools/gtk_settings.py::remove_theme_name`'s line-surgery style and `tools/atomic_write.py`); when the value is foreign, empty or absent, leave the file byte-identical; when the file is absent, succeed with a note. Every outcome other than a clear rewrite prints an `apply-gtk`-style stderr note naming the path: absent file ("nothing to clear"), foreign or absent value ("left untouched"), and after clearing, that widgets draw the engine's built-in default theme on their next start following this removal (the implementer grounds that fallback claim against the upstream Kvantum 1.1.4 sources the project already reads for Kvantum adaptations, and records it like those adaptations — it is prose provenance, not a rendered-pixel assertion). Single file, single atomic replace, so no lock is added. Add Makefile target `remove-kvantum` (`require_python_ready` only; no DESTDIR guard or data-home lock — nothing under the data home is touched) with a `.PHONY` and help entry, so the help-pinning check stays exhaustive. Add a `## tooling` row in docs/invariants.md and its `tests/support/invariants.py` register entry, plus a `tests/test_remove_kvantum.py` module using the existing isolated-homes make-run support. README.md gains a `remove-kvantum` row in the Removing-the-theme table (clears only the engine selection; `make uninstall` still deletes the widget style; restart running Qt applications) and prerequisites prose stays as is. Existing `tests/test_apply_*` and Kvantum config tests stay byte-unchanged.

**Acceptance criteria.** With an isolated config home, `make remove-kvantum` on a `Kvantum/kvantum.kvconfig` holding `[General] theme=org.macos8.desktop` beside unrelated keys exits 0, leaves the file with every other byte identical and only the theme key removed, and prints the clearing note naming the path. With `theme=KvArc` (a foreign name), `theme=` (empty), a `[General]` without `theme`, or no file at all, the run exits 0, the disk file when present is byte-identical, and the note explains nothing of ours was cleared (absence notes the literal missing path). An unset or relative `HOME` with no absolute `XDG_CONFIG_HOME` exits 2 with a diagnostic naming `HOME`. Re-running after removal is idempotent (second run notes nothing to clear, bytes unchanged), and `make apply` afterwards re-selects the theme, so a clear-then-apply round trip works. `remove-kvantum` appears in `.PHONY` and `make help`; the README row and the new invariant row pass their register checks; `make check` is green after the final edit.

### Reference-pixel sampler: cap the vertical color-match interval report (planned 2026-11-04 by the plan role) — done 2026-11-04 by the feature role

**Goal.** Bound noisy `--find-color --match-column-runs` output while retaining full-region measurements. Source and archive-heading searches found vertical length filters and counts, and horizontal output caps, but no vertical color-match interval cap. This complements the preceding horizontal-cap entry and can merge independently: the vertical filter and report blocks already exist.

**Approach and files.** In `tools/sample_arguments.py::build_parser`, add optional `--max-match-column-runs N`, default None, using `positive_int`; `option_error` requires `--match-column-runs`. In `tools/sample_report_search.py::_search_match`, slice the completed column-major list after both inclusive vertical length filters and add `match.omitted_column_runs` (eligible count minus emitted count) when the cap is explicit, including zero. In `report_search`, print `omitted matching column runs: N` immediately after the vertical list. Keep `tools/sample_match_runs.py::_MatchRuns` unchanged: its count and longest summary precede report filtering, and `finish` sorts by `(x,y)`. This bounds output, not segmentation memory. Add `tests/test_sample_match_column_runs_limit.py` using `CliTestCase` and the generated PNG pattern in `TestSampleMatchColumnRunsMaxLength`; document the flag beside vertical filters in README.md and extend the vertical-filter tooling row in docs/invariants.md. These five changed files constitute one run; pagination and collector optimization are outside this plan.

**Acceptance criteria.**

- For a 2x9 crop at absolute origin (2,1), column zero matches relative rows {0,2,3,5,6,7} and column one matches {8}. Cap 2 emits exactly `(2,1,1)` and `(2,3,2)` as `{x,y,length}` records with 2 omitted. Cap 3 adds `(2,6,3)` with 1 omitted, detecting a cap restarted per column. Maximum length 2 plus cap 2 emits the leading pair with 1 omitted; minimum length 2 plus cap 1 emits `(2,3,2)` with 1 omitted. Contradictory length cutoffs yield an empty list with zero omitted. Cap 4 or larger includes the bottom-flushed `(3,9,1)` and reports zero omitted; no matches produce an empty list with zero omitted.
- With summaries requested, count remains 7, column-run count remains 4 and longest column run remains `(2,6,3)` despite capping. Bounds, fraction, centroid, horizontal intervals, row/column diagnostics and coordinate paging match uncapped results. Include adjacent unequal RGB values accepted by tolerance and an exact-alpha rejection that splits an interval, checking literal capped records; stored RGB beneath alpha zero remains searchable. JSON and text expose the same prefix and omitted count. Without the option, neither the new member nor text line appears.
- Zero, negative, fractional, malformed, non-ASCII and missing caps exit 2 with empty stdout. A valid cap with `--find-color` but without `--match-column-runs` fails before reading a missing image and names the required flag. Help describes the dependency; direct-script and package output agree. README distinguishes interval count from pixel length and states filtering precedes capping; the invariant row names the new tests. `make check` passes after the final edit.
